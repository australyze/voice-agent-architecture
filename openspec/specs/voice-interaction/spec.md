# voice-interaction Specification

## Purpose

Defines the provider-independent voice-turn contract and the runtime behavior that accepts a validated turn and returns a deterministic placeholder reply, without treating a voice vendor as the agent or session system of record.

## Requirements

### Requirement: Voice turns use an internal provider-independent contract

The runtime MUST represent an inbound voice interaction as an internal contract that does not use a voice-vendor type. The contract MUST include, when available: a session identifier, an interaction or request identifier, the received input text, a timestamp, an event type, and opaque correlation metadata. Provider call identifiers MUST be stored only as opaque external channel identifiers, not as domain identity.

#### Scenario: Valid turn carries correlation fields

- **WHEN** the runtime receives a validated inbound voice turn with session, interaction, and request identifiers
- **THEN** those identifiers are present on the internal contract and are usable for logging and debugging

#### Scenario: Contract has no vendor types

- **WHEN** a reviewer inspects domain and application representations of a voice turn
- **THEN** those representations do not import or embed a voice-vendor SDK type or vendor-native payload schema

### Requirement: Media identity is not business state

The runtime MUST keep channel or media identity distinct from product business state. This change MUST NOT introduce conversational memory or persist Session or ConversationTurn tables. A successful placeholder turn MUST NOT advance a product workflow.

#### Scenario: Successful placeholder does not create business state

- **WHEN** the runtime handles a valid voice turn
- **THEN** it returns a deterministic reply without writing a product Session aggregate or changing a business workflow status

#### Scenario: External channel id stays opaque

- **WHEN** an inbound turn includes a provider call or conversation identifier
- **THEN** the runtime treats it as an opaque external channel identifier and does not use it as the internal session primary identity unless no internal session identifier was supplied

### Requirement: Runtime returns a deterministic placeholder reply

Given a valid internal voice turn, the application runtime MUST produce a deterministic structured reply owned by the runtime. The reply MUST NOT be generated by an LLM, product agent, or voice-vendor prompt. Locale for the placeholder text MUST come from configuration, not from a hard-coded domain language rule. The default configured locale for the first smoke is Spanish (`es`).

#### Scenario: Valid turn yields placeholder reply

- **WHEN** the runtime handles a valid voice turn
- **THEN** it returns a structured reply with placeholder text selected from the configured locale and does not call an LLM port

#### Scenario: Same input is deterministic

- **WHEN** the runtime handles two equivalent valid voice turns with the same configured locale
- **THEN** the structured reply content is the same

### Requirement: Runtime is invocable without a voice vendor

The voice-turn use case MUST be executable through the internal contract alone. Tests and local invocation MUST NOT require a voice-vendor account, SDK, or network call.

#### Scenario: In-process invocation without vendor

- **WHEN** a test supplies a valid internal voice turn to the runtime use case
- **THEN** the use case returns a structured reply or typed voice error without importing or calling a voice vendor

### Requirement: Voice errors are typed and safe

The runtime MUST classify voice-handling failures with stable codes covering at least: invalid payload, invalid session, unsupported event, timeout, configuration error, provider error, and internal runtime error. Internal exception details, stack traces, and secrets MUST NOT be placed on the structured reply returned to an adapter.

#### Scenario: Runtime failure is typed

- **WHEN** the voice-turn use case fails because of an internal error or a bounded timeout
- **THEN** the result is a typed voice error with a stable code and a safe message

#### Scenario: Timeout is bounded

- **WHEN** handling a voice turn exceeds the configured handling timeout
- **THEN** the runtime returns a timeout voice error and does not leave an unbounded wait

#### Scenario: Successful turn cancels the handling timer

- **WHEN** a voice turn completes before the handling timeout
- **THEN** the runtime cancels the timeout timer and MUST NOT emit an unhandled rejection from that timer

### Requirement: Voice turns emit correlatable secret-safe logs

Each handled voice turn MUST emit a structured log that, when the values are available, includes session identifier, request identifier, interaction identifier, timestamp, event type, processing time, and status. Logs MUST NOT contain API keys, credentials, or unnecessary sensitive payload fields.

#### Scenario: Successful turn is correlatable

- **WHEN** a valid voice turn completes
- **THEN** a success log includes the available correlation identifiers, event type, processing time, and a success status

#### Scenario: Failed turn is correlatable

- **WHEN** a voice turn fails
- **THEN** a failure log includes the available correlation identifiers, a stable error code, and no secret values

#### Scenario: Invalid session identifier is not logged raw

- **WHEN** the runtime rejects a turn because the session identifier is not a UUID
- **THEN** the failure log includes a stable session-invalid code and MUST NOT include the raw invalid identifier
